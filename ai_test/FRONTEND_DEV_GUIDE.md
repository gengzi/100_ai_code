# 前端开发细则（React）

适用范围：可视化配置与拖拽式接口自动化测试前端项目。本文作为团队统一的开发规范与迭代基础。

## 1. 目标与原则
- 统一交互与组件规范，避免重复造轮子。
- 约束技术选型与工程实践，提升可维护性与交付效率。
- 保持可扩展性，满足可视化编排、拖拽、配置化场景。

## 2. 技术栈与依赖约束
- React 18 + TypeScript。
- 状态管理：优先 React Context + hooks；复杂全局状态可采用 Redux Toolkit 或 Zustand（二选一）。
- 路由：React Router v6。
- UI 组件：优先自研组件库；允许使用 Ant Design 但需统一主题与二次封装。
- 拖拽：统一使用一套拖拽库（示例：dnd-kit 或 react-flow）。
- 图标：统一使用一个图标库（如 @ant-design/icons 或 lucide-react）。
- 构建：Vite 优先；需要 SSR 时再评估其他方案。

## 3. 项目结构约定
- src/
  - app/ 应用入口与全局配置（路由、主题、初始化）。
  - pages/ 路由级页面（按业务域拆分）。
  - features/ 业务功能模块（每个模块自包含 components、hooks、state、services）。
  - components/ 跨模块可复用组件。
  - hooks/ 通用 hooks。
  - services/ 网络请求与 API 聚合。
  - stores/ 全局状态（如 Redux/Zustand）。
  - utils/ 通用工具函数。
  - types/ 类型定义与接口。
  - assets/ 静态资源。
- 目录命名使用小写加短横线或小写驼峰，保持全局统一。

## 4. 编码规范
- 强制 TypeScript 严格模式。
- 组件命名：PascalCase；文件名与组件一致。
- hooks 命名：useXxx。
- 函数/变量命名：camelCase，语义化。
- 避免 any；必要时用 unknown 并做类型守卫。
- 只在复杂逻辑添加注释，注释要求简洁明了。

## 5. React 组件规范
- 组件职责单一，拆分到可复用层级。
- 业务逻辑与 UI 分离：容器组件负责数据与逻辑，展示组件仅接收 props。
- 组件 props 必须有类型定义。
- 需要 memoization 时才使用 memo/useMemo/useCallback，避免过度优化。

## 6. 状态管理规范
- 局部状态优先：能放组件内就不放全局。
- 全局状态必须有清晰的边界与描述。
- 异步状态统一管理：loading/error/data 模式明确。
- 避免循环依赖，跨模块状态通过公共层暴露。

## 7. 视觉与交互规范
- 可视化编排区域需保持清晰的层级与对齐线提示。
- 拖拽交互要支持撤销/重做（后续迭代可实现）。
- 配置面板与画布保持一致的交互模型。
- 统一主题与色彩系统，避免“局部风格”。

## 8. API 与数据规范
- API 层统一封装在 services/。
- 统一处理错误码与异常提示。
- 请求与响应类型强约束。
- 禁止在组件内直接写 fetch/axios。

## 9. 质量与测试
- 单元测试覆盖核心逻辑（hooks、utils、状态逻辑）。
- 关键交互路径需有 E2E 用例（后续按需补充）。
- 每次迭代必须通过 lint 与 build。

## 10. 代码评审与协作
- PR 必须包含变更说明、影响范围、测试结果。
- 同一功能模块变更尽量合并提交，避免碎片化。
- 禁止在主分支直接提交。

## 11. 版本与迭代约定
- 功能需求必须先出配置稿或交互稿，再进入开发。
- 每个迭代记录关键决策与技术评审结论。
- 重要架构变更需同步更新本文档。

## 12. 文档维护
- 本文档为基础规范，后续可追加细化章节（如拖拽交互细则、配置 schema 规范）。
- 任何更新需在版本历史中记录。
